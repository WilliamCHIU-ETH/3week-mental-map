## 目前的核心概念

1. **AI 的速度受限於問題清楚度。** 我目前懷疑，Prototype 慢不是單純的生成能力問題，而是我太早讓 AI 實作。
2. **0→1 要先探索，再規格化。** Scrum 可以承接已經被說清楚的工作，但不能代替目標使用者、痛點、產品價值與形狀的探索。
3. **完整不等於功能很多。** 本週要完整的是核心價值的使用者路徑，不是做出市面產品的所有功能。
4. **Prototype 不是驗證結果。** 它先把假設變成別人能操作、能挑戰的東西；真正的驗證來自目標使用者互動後的反應與行為。
5. **決策溝通也是要解的產品問題。** 本週不只要讓產品前進，也要讓決策者在短時間看見方向、取捨、調整與下一步。
6. **先解痛點，再測是否契合市場。** 現階段不能先宣稱 Product-Market Fit；應先提出能解痛點的產品，再透過真人測試判斷是否成立。

## 數據邏輯的校準

目前曾用兩個不同來源的量體進行比較：

- 外部來源：整體市場的活躍人口。
- 內部來源：公司既有產品的活躍使用量。

這個比值目前只能說明「兩個量體的相對大小」，**不能直接稱為覆蓋率，也不能推論兩者差額都是未被服務的潛在使用者**。原因是兩邊的身分是否重疊、口徑是否完全可比，以及差額人口的需求與痛點都還不知道。

因此，需求與市場視角提出的挑戰仍成立：這組數字可以用來提出問題，卻還不能單獨證明產品存在的必要性。要讓它變成更強的證據，仍需要：

1. 確認分子與分母的身分和統計口徑能否對齊。
2. 說清楚新產品真正想服務的是哪一群人，而不是把量體差額全部當成目標。
3. 透過訪談、Prototype 測試或其他使用者證據，確認他們是否真的有「資訊太多、無法抓重點」的痛點。

## 本週的 Decision Lock

**本輪要決定：** 這套「先探索、再拆 Activity／Task／驗收場景、最後交給 AI 實作」的方法，能否在短期交付窗口內產出一個完整且可供決策者與使用者挑戰的 Core Journey Prototype。

**影響範圍：** 本週 Prototype 的工作方式與決策溝通，不延伸到 Go-to-Market、正式部署或完整產品開發制度。

**必要證據：**

- Prototype 能從入口走完一條核心使用者路徑。
- 體驗中能看懂產品主動挑資訊、講重點的差異。
- 使用接近真實情境的資料，不只是抽象示意。
- 每個關鍵 Task 有可觀察的驗收條件。
- 至少能取得決策者或目標使用者對核心假設的具體挑戰。

**停止條件：**

- 若有限時間內仍主要靠逐像素、逐文案 prompt 才能前進，先停止擴功能，檢查是不是上游 Journey、Task 或驗收條件仍不清楚。
- 若完整路徑做出來仍無法讓人說出產品價值，不以美化畫面掩蓋，回到目標使用者、痛點與 Product Intent。
- 若測試對象不是目標使用者，只把結果視為 Prototype 可理解性回饋，不宣稱痛點或 Product-Market Fit 已被驗證。

## 一句話收斂

**我這週要驗證的，不只是某個新產品 Prototype 能不能做出來，而是能否把 0→1 的模糊產品思考，轉成一條 AI 做得快、決策者看得懂、使用者能實際挑戰的完整工作鏈。**
